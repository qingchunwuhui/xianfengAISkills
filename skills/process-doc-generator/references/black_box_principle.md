# 黑匣子原则 (The Black Box Principle)

## 核心理念

当我们在提取对话和生成过程文档时，只遵循一个最高标准 —— **No Look Back (绝不回头)**。

## 测试标准

假设两个月后，你在这个项目上：
- **失忆了**（完全忘记了当时的上下文）
- **断网了**（无法搜索、无法问AI）
- **只有这篇笔记**

问自己：
- 你能不能**完整复现**当时的解决方案？
- 你能不能**瞬间理解**当时的思考脉络？

### 判定结果

- 如果能 → **✅ 入库**（这是合格的过程文档）
- 如果不能 → **❌ 垃圾**（需要补充完善）

## 为什么叫"黑匣子"？

就像飞机的黑匣子一样，它记录的不是"飞机飞得很好"或"飞行员很棒"这种总结，而是：
- 每一秒的飞行数据
- 每一次操作的参数
- 每一个异常的完整堆栈

**目的**：让调查人员在事后能够**完整还原**当时发生了什么。

我们的过程文档也是如此：不是事后总结，而是**高保真还原**。

## 黑匣子文档 vs 垃圾文档

### ❌ 垃圾文档的特征

```markdown
# Bug修复记录

遇到了一个报错，经过多次调试，最终解决了。

解决方案：修改了配置文件。
```

**为什么是垃圾？**
- 报错是什么？没写。
- 调试了几次？做了什么？没写。
- 配置文件改了什么？没写。
- 为什么改这个就能解决？没写。

两个月后你看到这个，除了"哦，我以前遇到过这个问题"之外，**没有任何帮助**。

### ✅ 黑匣子文档的特征

```markdown
# Bug修复记录

## 问题
在执行 `npm run build` 时报错：
```
ERROR in ./src/index.js
Module not found: Error: Can't resolve 'react-router-dom'
```

环境：
- Node.js: v18.12.0
- npm: 8.19.2
- OS: Windows 11

## 解决方案
在 package.json 中添加缺失的依赖：
```json
"dependencies": {
  "react-router-dom": "^6.4.3"
}
```

执行 `npm install` 后，重新 build 成功。

## 过程
第一次尝试：
- 操作：直接 `npm install react-router-dom`
- 结果：安装成功，但 build 仍然报错
- 分析：可能是版本问题

第二次尝试：
- 操作：删除 node_modules，重新 `npm install`
- 结果：还是报错
- 分析：查看 package.json，发现 dependencies 里没有这个包

第三次尝试：
- 操作：手动在 package.json 添加 `"react-router-dom": "^6.4.3"`
- 操作：执行 `npm install`
- 结果：✅ 成功，build 通过

## 思考
坑点：直接 `npm install <package>` 不会自动添加到 package.json（在 npm 5+ 版本需要加 `--save` 或使用 `npm install` 默认会添加，但这里可能是其他原因）

原理：package.json 是项目依赖的"清单"，如果清单里没有，CI/CD 环境就无法安装。

避坑：以后安装依赖，记得检查 package.json 是否正确更新。
```

**为什么合格？**
- 报错信息完整（包括堆栈）
- 环境参数清楚（Node、npm、OS版本）
- 试错过程完整（第一次做了什么，为什么失败）
- 解决方案具体（不是"修改配置"，而是"在哪个文件的哪里加了什么"）
- 思考有价值（说明了为什么会错，以后怎么避开）

两个月后你看到这个，即使完全忘记了，也能：
1. 理解当时遇到了什么问题
2. 知道为什么会遇到这个问题
3. 知道怎么解决
4. 知道以后怎么避免

## 黑匣子清单

在完成过程文档后，用这个清单检查：

### 基础信息
- [ ] 问题描述完整且具体（不是"报错了"，而是"在执行X操作时报错Y"）
- [ ] 环境参数清楚（版本号、OS、依赖库）
- [ ] 报错信息完整（包括完整的 Error Stack）

### 视觉元素（重要性最高）
- [ ] **所有截图都保留了**
  - Obsidian 图片引用：`![[image.png]]` 一个都不能丢
  - 不要简化为"见下图"或删除
  - 每张截图要有说明

- [ ] **日志输出完整保留**
  - 成功列表：完整的工具列表、安装位置
  - 失败列表：具体的错误提示
  - 不要概括为"安装成功"或"部分失败"

- [ ] **界面细节清楚**
  - 具体的菜单位置（如"选择Global"）
  - 选项名称（如"Copy" vs "Symlink"）
  - 界面上的文本和提示

### 过程记录
- [ ] **真实性保证**
  - 没有虚构不存在的"试错过程"
  - 操作次数真实（1次就是1次，不虚构多次）
  - 没有添加原文没有的"认知升级"

- [ ] **完整性保证**
  - 试错路径完整（每次尝试了什么，结果如何）
  - 失败的尝试保留了（"此路不通"比"正确答案"更重要）
  - 关键转折点清楚（哪个线索是突破口）

### 解决方案
- [ ] 代码/配置完整可执行（不是伪代码，是真实代码）
- [ ] 操作步骤清晰（一步一步，不跳步）
- [ ] 前置条件说明（如果有依赖，要写清楚）

### 思考复盘
- [ ] 坑点分析（为什么会错）
- [ ] 底层原理（不只是how，还有why）
- [ ] 避坑指南（以后怎么预防）
- [ ] **不强求填满**：没有深刻洞察就不写

### 原始记录（新增章节）
- [ ] **保留第一手资料**
  - 完整的日志输出在"原始记录"区
  - 关键对话片段保留
  - 相关文件路径清楚

### 最终测试
- [ ] **两个月后失忆测试**：只看这篇文档，能否完整复现？
- [ ] **断网测试**：不能搜索，文档信息足够吗？
- [ ] **新手测试**：陌生人能看懂并执行吗？

## 常见误区

### 误区1：过度总结

❌ "经过分析，发现是配置问题"
✅ "查看报错堆栈，发现是 webpack.config.js 第45行的 publicPath 配置错误，应该是 '/' 而不是 '/dist/'"

### 误区2：省略失败尝试

❌ 只记录最终成功的方案
✅ 记录所有尝试，特别是失败的尝试（它们是避坑指南）

### 误区3：缺少上下文

❌ "运行这个命令就能解决"
✅ "在 X 环境下，使用 Y 版本的工具，运行 Z 命令，注意需要先..."

### 误区4：只有代码，没有思考

❌ 只贴代码，不解释为什么
✅ 代码 + 为什么这样写 + 背后的原理

## 实战案例对比

### 案例1：修复 CORS 错误

**垃圾版本**：
```
遇到 CORS 错误，在后端加了 CORS 头就好了。
```

**黑匣子版本**：
```
## 问题
前端 React 应用调用后端 API 时报错：
"CORS policy: No 'Access-Control-Allow-Origin' header is present"

环境：
- 前端：React 18.2.0, localhost:3000
- 后端：Express 4.18.0, localhost:5000

## 过程
第一次尝试：在前端 fetch 添加 mode: 'no-cors'
- 结果：不报错了，但拿不到数据
- 分析：no-cors 只是绕过报错，实际还是被浏览器拦截了

第二次尝试：在后端添加 CORS 中间件
- 操作：npm install cors
- 操作：在 app.js 添加 app.use(cors())
- 结果：✅ 成功

## 解决方案
后端代码（app.js）：
```javascript
const cors = require('cors');
app.use(cors()); // 在所有路由之前添加
```

## 思考
原理：CORS 是浏览器的安全机制，需要服务器响应头允许跨域
坑点：no-cors 不是解决方案，只是绕过报错
正确做法：服务器端配置 CORS 头
```

看出区别了吗？黑匣子版本记录了：
- 完整的报错信息
- 环境参数（版本号、端口）
- 失败的尝试（no-cors）及为什么失败
- 完整的解决方案（代码+位置）
- 底层原理（CORS 机制）

## 总结

黑匣子原则的本质是：**把未来的你当作一个完全不知情的人，你需要给他提供足够的信息，让他能够完整复现你的解决方案。**

### 三个核心要素

1. **视觉元素（最重要）**
   - 截图：操作界面、错误提示、最终结果
   - 日志：完整的输出，不简化
   - 图表：流程图、架构图、示意图

2. **文本记录**
   - 完整的报错堆栈
   - 具体的操作步骤
   - 环境参数和配置

3. **思考路径**
   - 为什么做这个决策
   - 失败尝试的教训
   - 底层原理的理解

### 保真优先级

```
截图 > 日志 > 代码 > 文字描述
```

**原因**：
- 截图最直观，两个月后一眼就能认出界面
- 日志最准确，不会有记忆偏差
- 代码最具体，可以直接复制执行
- 文字描述最容易失真，记忆会美化过程

### 最终原则

**记住：代码会过时，技术会更新，但思考的路径和决策的上下文是永恒的资产。**

**追加：截图会说话，日志不会骗人，真实的记录比完美的结构更重要。**
