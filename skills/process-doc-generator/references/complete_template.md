# 完整过程文档模板 (Complete Process Doc Template)

此模板用于生成高保真的实战过程文档，遵循"黑匣子原则"，确保未来能完整复现。

## 模板选择指南

### 轻量版模板（推荐优先使用，适合80%场景）

适用场景：
- 单次操作记录
- 配置流程记录
- 简单问题解决
- 工具使用记录

**关键特征**：
- 只有1-2次操作，没有复杂试错
- 重点是记录"怎么做"，而不是"为什么这样做"
- 保留所有截图和日志，但不需要深度思考

---

### 完整版模板（适合20%的复杂场景）

适用场景：
- 复杂Bug修复的完整记录
- 技术难题的试错路径还原
- 架构决策的上下文记录
- 需要深度复盘的实战项目

**关键特征**：
- 有真实的多次试错过程
- 需要记录决策上下文和思考路径
- 有认知升级或深刻洞察

---

## 填写指南

### 选择合适的模板

**优先使用轻量版**：
- 如果只有1-2次操作 → 轻量版
- 如果是配置流程、工具使用 → 轻量版
- 如果没有深度思考 → 轻量版

**使用完整版的条件**：
- 有真实的3次以上试错过程
- 涉及复杂的决策和分析
- 有明确的认知升级

**不确定时 → 选择轻量版**

---

### 保真原则（最重要）

**必须保留的元素**：
1. **所有截图引用**
   - ✅ 保留：`![[PixPin_2026-02-05_13-32-09.webp]]`
   - ❌ 删除：不要简化为"见下图"

2. **完整日志输出**
   - ✅ 保留：完整的成功列表和失败列表
   - ❌ 简化：不要概括为"安装成功"

3. **具体操作细节**
   - ✅ 保留：选择了"Copy"方式，位置在全局目录
   - ❌ 简化：不要写成"安装技能"

4. **原始对话**
   - ✅ 保留：关键的分析过程和问答
   - ❌ 删除：不要只保留结论

---

### 真实性原则（避免虚构）

**❌ 严禁操作**：
1. **不要虚构试错过程**
   - 如果只有一次操作，就记录一次
   - 不要为了填充"第一次、第二次"而编造内容

2. **不要添加不存在的章节**
   - 如果没有认知升级，就不写这个章节
   - 如果没有深刻洞察，就不写核心洞察

3. **不要过度提炼**
   - 保留原始的口语化表达
   - 不要把具体操作抽象为理论

**✅ 正确做法**：
- 有多少材料写多少
- 保持原始记录的真实性
- 允许结构不完整

---

### Process 章节的关键

**不要写**：
❌ "经过多次尝试，最终解决了问题"（这是事后总结）
❌ "调试了很久，发现是配置问题"（太笼统）

**要写**：
✅ "第一次尝试：修改了 X 配置，报错 Y，说明..."
✅ "第二次尝试：根据报错信息，猜测是 Z 的问题，验证后发现..."
✅ "第三次尝试：参考了官方文档的 W 部分，修改为..."

### Thinking 章节的关键

**不要写**：
❌ "这个问题很有意思"（废话）
❌ "学到了很多"（空洞）

**要写**：
✅ "坑点：之前以为 A 和 B 是一回事，实际上..."
✅ "原理：这个报错的根因是 C 机制，它的工作原理是..."
✅ "认知升级：以前不理解 D，现在明白了 D 本质上是..."

## 黑匣子测试清单

**终极测试**：两个月后失忆测试
- 假设你完全忘记了这件事
- 假设你断网了，无法搜索
- 只看这个文档，能否完整复现？

### 基础信息检查
- [ ] 问题描述完整且具体（不是"报错了"，而是"在执行X操作时报错Y"）
- [ ] 环境参数清楚（版本号、OS、依赖库）
- [ ] 报错信息完整（包括完整的 Error Stack）

### 视觉元素检查（新增，最重要）
- [ ] **所有截图都保留了吗？**
  - 检查原文有几张截图
  - 确认新文档中的截图引用数量相同
  - 不要用"见下图"替代具体的图片引用

- [ ] **日志输出完整吗？**
  - 成功列表完整保留
  - 失败列表完整保留
  - 不要简化为一句话概括

- [ ] **操作界面细节保留了吗？**
  - 具体的菜单位置
  - 选项的名称（如"Copy" vs "Symlink"）
  - 界面上显示的文本

### 过程记录检查
- [ ] **真实性检查**
  - 是否虚构了不存在的"试错过程"？
  - 是否添加了原文没有的"认知升级"？
  - 操作次数是否真实（1次就是1次，不要写成多次）

- [ ] **完整性检查**
  - 试错路径完整（每次尝试了什么，结果如何）
  - 失败的尝试保留了（"此路不通"比"正确答案"更重要）
  - 关键转折点清楚（哪个线索是突破口）

### 解决方案检查
- [ ] 代码/配置完整可执行（不是伪代码，是真实代码）
- [ ] 操作步骤清晰（一步一步，不跳步）
- [ ] 前置条件说明（如果有依赖，要写清楚）

### 思考复盘检查
- [ ] 坑点分析（为什么会错）
- [ ] 底层原理（不只是how，还有why）
- [ ] 避坑指南（以后怎么预防）

### 原始记录检查（新增）
- [ ] **原始素材保留了吗？**
  - 完整日志输出在"原始记录"章节中
  - 关键对话片段保留
  - 相关文件路径清楚

### 复现性验证
- [ ] **失忆测试**：两个月后失忆，能否只看文档完整复现？
- [ ] **断网测试**：不能搜索，文档中的信息足够吗？
- [ ] **新手测试**：一个不了解这个问题的人，能否看懂并执行？

---

## 质量标准

### ✅ 优秀文档的特征
- 所有截图完整保留，有明确的说明
- 日志输出完整，成功和失败都清楚
- 操作步骤具体到界面位置和选项名称
- 真实记录，不虚构试错过程
- 有原始记录章节，保留第一手资料

### ❌ 不合格文档的特征
- 截图被删除或简化
- 日志被概括为一句话
- 只有抽象的"第一次、第二次尝试"，没有具体操作
- 添加了原文没有的"认知升级"
- 缺少原始记录，无法验证

---

## 改进建议总结

基于实际使用反馈，重点改进：
1. **保真优先**：不丢失任何截图、日志、代码
2. **真实性**：不虚构试错，不添加不存在的内容
3. **模板灵活**：轻量版适合大部分场景，完整版仅用于复杂问题
4. **原始记录**：新增章节专门保留第一手资料
5. **检查清单**：增加视觉元素和真实性检查项
