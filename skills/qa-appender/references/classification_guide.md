# 知识分类指南 (Knowledge Classification Guide)

## 核心问题

当你通过对话获得了一个问答内容时，应该：
- **追加到原文**（依附型）
- **新建独立卡片**（独立型）

这个指南帮你做出正确判断。

---

## 判断标准

### 依附型（Context Heavy）→ 追加到原文

**核心特征**：离开原文背景就看不懂

**判断方法**：
如果把这个问答单独拿出来，脱离原文，问另一个人"这是什么意思"，他会不会回答"你在说什么？"

如果会 → **依附型**，应该追加到原文

**典型场景**：
1. **针对具体代码的补充说明**
   - 例：原文是"修复了 app.js 的 CORS 问题"
   - 问答："为什么要在第15行添加那个中间件？"
   - 判断：脱离原文，看不懂"第15行"是什么

2. **对原文细节的深挖**
   - 例：原文是"使用 Promise.all 并行处理"
   - 问答："为什么这里用 Promise.all 而不是 Promise.race？"
   - 判断：脱离原文，不知道"这里"是哪里

3. **基于原文案例的扩展**
   - 例：原文是"在 Windows 下配置 swap"
   - 问答："如果是 Linux 呢？"
   - 判断：脱离原文，不知道在讨论什么

4. **对原文决策的解释**
   - 例：原文是"选择了方案A而不是方案B"
   - 问答："为什么方案B不行？"
   - 判断：脱离原文，不知道方案A和B是什么

### 独立型（Atomic Concept）→ 新建卡片

**核心特征**：可以脱离原文单独理解

**判断方法**：
如果把这个问答单独拿出来，给另一个人看，他能不能理解这是一个独立的知识点？

如果能 → **独立型**，应该新建卡片

**典型场景**：
1. **通用概念的解释**
   - 例："什么是 CORS？"
   - 判断：这是一个独立的技术概念，可以单独理解

2. **独立的技巧或方法**
   - 例："如何在 Git 中撤销上一次提交？"
   - 判断：这是一个独立的操作技巧，不依赖具体场景

3. **通用的原理说明**
   - 例："为什么 JavaScript 的 this 指向会变化？"
   - 判断：这是一个语言机制，可以独立讨论

4. **工具或库的使用方法**
   - 例："ripgrep 和 grep 的区别是什么？"
   - 判断：这是对两个工具的对比，可以独立理解

## 实战案例对比

### 案例1：依附型 vs 独立型

**原文背景**：你写了一篇笔记，记录了"修复 React 应用的 CORS 错误"

#### 问答A："为什么这里用 cors() 而不是手动设置头？"

**判断**：依附型
- **原因**："这里"指的是原文中的具体代码
- **脱离测试**：单独看这个问题，不知道在讨论什么
- **行动**：追加到原文的 Q&A 章节

#### 问答B："什么是 CORS？为什么浏览器要有 CORS 机制？"

**判断**：独立型
- **原因**：这是一个通用的概念解释
- **脱离测试**：单独看这个问题，可以理解是在问 CORS 的定义
- **行动**：新建独立卡片（比如命名为"CORS跨域资源共享机制"）

---

### 案例2：边界情况

**原文背景**：你记录了"在 Linux 下配置 swap 文件"

#### 问答："如果 swap 文件大小不够了怎么办？"

**判断**：依附型（有争议，可能是独立型）

**分析**：
- 如果问题是"**在这个配置下**，如果 swap 不够了怎么办"→ 依附型
- 如果问题是"**一般情况下**，swap 文件不够了怎么办"→ 独立型

**建议**：
- 如果不确定，**优先选择依附型**
- 原因：追加到原文更容易找到，因为有完整的上下文

---

## 判断流程图

```
问自己：把这个问答单独拿出来，别人能看懂吗？
│
├─ 能看懂 → 这是一个独立的概念/技巧
│   └─ 新建独立卡片
│
└─ 看不懂 → 需要原文的上下文才能理解
    └─ 追加到原文
```

## 追加到原文的格式

在原文末尾添加 `## 💡 实战答疑 (Q&A)` 章节：

```markdown
---
[原文的 Problem、Solution、Process、Thinking]
---

## 💡 实战答疑 (Q&A)

### Q: [问题摘要]

**📝 核心结论**
[干货结论]

````ad-note
title: 📸 当时的实战场景
[原始对话]
```

### Q: [另一个问题]
...
````

## 新建独立卡片的格式

创建一个新的 markdown 文件：

```markdown
---
type: 概念卡片
class: 核心认知
level: A
tags: [概念, {具体技术栈}]
---

# [概念名称]

## 定义 (Definition)
[用一句话说清楚这是什么]

## 核心要点 (Key Points)
- 要点1
- 要点2
- 要点3

## 实战示例 (Example)
[具体的代码示例或使用场景]

## 注意事项 (Notes)
[常见误区、避坑指南]

## 来源 (Source)
**对话时间**：{YYYY-MM-DD}
**相关主题**：[链接到相关的实战笔记]
```

## 常见误区

### 误区1：什么都新建独立卡片

❌ **错误思路**：
"这个知识点很重要，应该新建独立卡片"

✅ **正确思路**：
"这个知识点能否脱离原文单独理解？"

**例子**：
- 原文：修复了 useEffect 的依赖问题
- 问答："为什么这里要加 userId 到依赖数组？"
- 错误判断：这是关于 useEffect 的知识，应该新建卡片
- 正确判断：这是针对原文代码的解释，应该追加到原文

### 误区2：什么都追加到原文

❌ **错误思路**：
"这个问答是在讨论原文的内容，应该追加"

✅ **正确思路**：
"这个问答是对原文的补充，还是一个独立的概念？"

**例子**：
- 原文：使用 Promise.all 并行处理
- 问答："Promise.all 和 Promise.race 的区别是什么？"
- 错误判断：原文提到了 Promise.all，应该追加
- 正确判断：这是对两个 API 的通用对比，应该新建卡片

## 实战检验

### 检验方法1：时间旅行测试

**假设**：两个月后，你完全忘记了原文的内容

**问**：只看这个问答，你能理解吗？
- 能理解 → 独立型
- 不能理解 → 依附型

### 检验方法2：新人测试

**假设**：你把这个问答发给一个完全不了解背景的新人

**问**：他能理解这是在说什么吗？
- 能理解 → 独立型
- 不能理解（会问"你在说什么？"）→ 依附型

### 检验方法3：搜索测试

**假设**：你在搜索引擎搜索这个问题的关键词

**问**：返回的结果应该是原文，还是独立的解释页面？
- 独立的解释页面 → 独立型
- 原文（因为需要上下文）→ 依附型

---

## 边界情况处理

### 情况1：有一定独立性，但和原文强相关

**例子**：
- 原文：实现了 JWT 认证
- 问答："JWT 和 Session 的区别是什么？"

**分析**：
- 这个问答可以独立理解（JWT vs Session 是通用对比）
- 但它是从原文的 JWT 实现引出的

**建议**：
- **优先新建独立卡片**（因为它是通用知识）
- 在原文的 Q&A 章节添加一个简短的引用：
  ```markdown
  ## 💡 实战答疑 (Q&A)

  ### Q: 为什么选择 JWT 而不是 Session？
  参考独立卡片：[[JWT vs Session 对比]]
  ```

### 情况2：对原文的深度扩展

**例子**：
- 原文：配置了 webpack
- 问答："webpack 的工作原理是什么？"

**分析**：
- 这个问答可以独立理解（webpack 原理是通用知识）
- 但如果原文是在讲"如何配置 webpack 的某个具体问题"，那这个问答可能只是为了解释"为什么要这样配置"

**建议**：
- 如果问答是为了解释原文的配置 → 追加到原文
- 如果问答是独立的原理讲解 → 新建卡片

---

## 总结

**判断的黄金法则**：
> 脱离原文，能否独立理解？
> - 能 → 独立型，新建卡片
> - 不能 → 依附型，追加到原文

**当不确定时**：
> 优先选择**依附型**（追加到原文）
> 原因：有完整上下文更容易找到，以后可以随时拆分成独立卡片

**记住**：
> 分类的目的是让未来的你能**快速找到答案**，不是为了完美的分类系统
